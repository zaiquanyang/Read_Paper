RE-TRAC: REcursive TRAjectory Compression for Deep Search Agents

agent arXiv abs PDF arXiv 2602.02486
核心思想：这篇论文最有价值的地方，不是单纯提出了一个“多跑几轮”的 agent trick，而是把 deep research agent 的核心瓶颈明确归因为 线性 ReAct 对长程分支搜索的承载不足，并用 trajectory compression + recursive state passing 给出了一个非常实用、易扩展、还能蒸馏到小模型中的解决方案。

问题与动机

这篇论文关注的是 Deep Research / web search agent 在长轨迹任务里的一个很具体但很致命的问题: 模型明明在前面规划过若干搜索分支，但随着 ReAct 轨迹不断变长，后面往往会忘掉这些分支，只沿着单一路径越走越深，最后错过真正有用的信息源。

作者把这个现象总结为 incomplete branch exploration。它不是单纯的“模型不会推理”，而是：

  • 任务本身需要多分支探索、回溯、交叉验证。
  • ReAct 的执行形态却是线性的 action-observation 链。
  • 当上下文极长、工具调用密集时，早期计划会被后续 observation 淹没。
  • 最终失败往往来自“本来该查的分支没查完”，而不是一点思路都没有。

论文对失败轨迹做了分析，在 BrowseComp 上统计到：

Model失败轨迹中存在 incomplete branches 的比例
GLM-4.793.0%
DeepSeek-V3.292.7%
Tongyi-DeepResearch83.4%

这组数字很关键，因为它说明现有 deep research agent 的失败，大量是“搜索管理失败”，而非“能力完全缺失”。

同时，作者还发现很多模型的 Pass@8 明显高于 Pass@1，这意味着模型并不是完全答不出来，而是在单次 rollout 中没有把搜索空间探索到位。

上图想表达的核心结论是：模型其实有潜力在多次尝试中找到正确答案，但传统的 independent rollouts 彼此隔离，无法复用经验，也会带来大量重复搜索。

方法核心

作者提出的方法叫 RE-TRAC，全称是 REcursive TRAjectory Compression。它不是再造一个复杂 agent 框架，而是在 ReAct 之上加了一个“跨 rollout 的经验压缩层”。

最核心的操作只有一句话：

\[S_t \leftarrow \mathrm{Compress}(\tau_t, S_{t-1}; \mathcal{C})\]

其中：

  • $\tau_t$ 表示第 $t$ 轮 rollout 的完整轨迹。
  • $S_{t-1}$ 表示上一轮累计下来的结构化状态。
  • $\mathcal{C}$ 表示固定的 compression specification。
  • $S_t$ 表示新的压缩状态，会被喂给下一轮 agent。

这背后的直觉是：

  • 不要把上一轮完整的超长轨迹原样塞回去。
  • 只保留对下一轮搜索真正有用的“高价值状态”。
  • 让后续 rollout 既知道“已经确认了什么”，也知道“还有哪些未完成分支值得继续查”。

对大模型，RE-TRAC 可以直接当作 inference-time prompting strategy 来用，不需要额外训练。作者把它用于：

  • o4-mini
  • o3
  • GPT-5-medium
  • DeepSeek-V3.2
  • GLM-4.7

然后和几种经典 test-time scaling 方案对比：

  • RT@n: RE-TRAC 跑 $n$ 轮后的最终答案
  • MV@n: $n$ 个独立 rollout 的多数投票
  • WV@n: 带自评置信度的加权投票
  • Best@n: 选自评置信度最高的答案

在 BrowseComp300 上，主要结果如下：

这个表最值得注意的地方有两个：

  • RE-TRAC 几乎在所有模型上都能稳定达到最佳或并列最佳。
  • 对自我判断能力没那么强的模型，RE-TRAC 比投票类方法更稳，因为它不依赖“谁更会给自己打分”，而是靠跨轮经验传递来扩展搜索。

上图说明了另一点：RE-TRAC 不只是效果好，而且更省资源。原因在于后续 rollout 会复用前面轮次的状态，不需要每一轮都从空白开始重复搜索，所以在 token 和 tool usage 上更经济。

实验与结论

作者在五个 deep research / search-heavy benchmark 上做了评测：

  • BrowseComp
  • BrowseComp-ZH
  • GAIA
  • XBench
  • HLE

主结果里最关键的几行如下：

ModelBrowseCompBrowseComp-ZHGAIAXBenchHLE
Tongyi-DeepResearch-30B-A3B43.446.770.975.032.9
RE-TRAC-30B-A3B53.057.378.283.031.5

NestBrowse-4B22.428.468.974.0-
RE-TRAC-4B30.036.170.476.622.2

作者据此想说明三件事：

  • 同尺寸最强

RE-TRAC-30B-A3B 相比底座 Tongyi-DeepResearch-30B-A3B，在 BrowseComp、BrowseComp-ZH、GAIA、XBench 上提升大约 8% 到 10%。

  • 小模型也能变强

RE-TRAC-4B 在 <15B 的开源 baseline 中表现最好，说明 RE-TRAC 不只是“更大的模型更会用”，而是可以把 long-horizon search 的套路教给小模型。

  • 能和更大模型竞争

RE-TRAC-30B-A3B 在若干 benchmark 上能逼近甚至超过更大参数量模型，说明“搜索管理”本身就能带来很大增益。

补充一点：在 HLE 上，RE-TRAC-30B-A3B 并没有超过 Tongyi-DeepResearch-30B-A3B，这也提醒我们 RE-TRAC 的优势更集中在 search-heavy、branch-heavy、trajectory-heavy 的任务，而不是所有类型能力都无条件上涨。

价值、局限与启发

如果把这篇工作放回你现在的 agent 主题下，我觉得最值得吸收的是下面几条：

如果你后面想把这篇工作的方法借到自己的 agent 实验里，我建议最小实现可以先做成这四步：

  • 保持现有 ReAct agent 不变。
  • 每轮 rollout 结束后，用固定模板生成三段式状态：
  • conclusions
  • verified evidence
  • unresolved branches
  • 下一轮把这份状态作为新的初始上下文输入。
  • 对比单轮 ReAct、Best-of-N、RE-TRAC 风格递归 rollout 的成功率与工具调用成本。

如果再进一步，可以专门加两个机制：

  • 一个 branch coverage 指标，统计“计划过但未执行”的分支比例。
  • 一个 summary quality 评估器，检查压缩状态是否遗漏关键未解决问题。
