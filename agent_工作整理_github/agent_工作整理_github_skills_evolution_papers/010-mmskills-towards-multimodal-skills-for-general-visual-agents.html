MMSkills: Towards Multimodal Skills for General Visual Agents

arXiv 2605.13527
agent arXiv abs PDF arXiv 2605.13527
核心思想：这篇论文最核心的贡献，是把 visual agent 的 skill 从“文本步骤”升级成“带有状态判别与多视角视觉证据的多模态 procedure package”，再通过 branch loading 避免上下文污染，让这些 skill 真正在 GUI 和游戏环境里变成可调用、可验证、可迁移的外部知识单元。

问题与动机

这篇工作的核心问题是: 现有 agent 的“skill”大多是文本 prompt、代码片段、执行脚本或抽象动作模板，但对于真正依赖视觉感知的 agent，这类 skill 只告诉模型“做什么”，却没有充分编码“当前画面是否处在该 skill 应该被调用的状态”“应该观察哪些视觉线索”“什么时候可以验证已经完成”。因此，传统 text-only skill 很难稳定支持 GUI agent、game agent 这类需要持续看图决策的系统。

作者把这一缺口概括为 multimodal procedural knowledge。也就是说，视觉 agent 需要复用的不只是步骤文本，还包括与步骤绑定的视觉状态、局部证据、状态转移前后对比，以及完成验证线索。文章的目标不是再做一个更大的 memory bank，而是提出一套适合 visual agent 的可复用技能表示、自动生成流程以及推理时的调用机制。

从问题设定上，这篇文章比“长时记忆”“经验回放”更聚焦于 skill packaging。它关心的不是把历史轨迹完整存下来，而是从公开轨迹中抽取出可迁移的、结构化的、多模态 procedural unit，并在运行时以低污染方式送给主 agent 使用。

方法核心

作者的方法 MMSkills 由三部分组成:

  • Multimodal Skill Package: 定义视觉 agent skill 的结构化表示。
  • Skill Generation Pipeline: 从公开的、非测试集轨迹中自动生成 skill 库。
  • Branch-loaded Multimodal Skill Agent: 在推理时通过“分支加载”方式调用 skill，避免把整包多模态内容直接塞进主上下文。

上图对应论文的总框架图。它非常清楚地表达了作者的主张: skill 不再只是文本 procedure，而是“文本 procedure + 状态卡片 + 多视角关键帧”；这些 skill 由 Generator 从公开轨迹中抽出来；运行时主 agent 不直接吃完整 skill，而是先开一个 branch 去筛选相关 state card 和 visual evidence，再把压缩后的 guidance 返回主 agent。

作者先给出整体执行范式。Generator 把公开轨迹集合 $\mathcal{T}=\{\tau_i\}$ 映射成 skill 库 $\mathcal{M}=\{M_i\}_{i=1}^{N}$。测试任务开始前，系统会根据 instruction 先召回候选 skill 集合 $\mathcal{C}_I \subset \mathcal{M}$。在线执行时，主 agent 有两种模式:

\[\begin{aligned} \text{direct}: \quad & A_t = \pi_{\text{main}}(O_t,H_t,\mathcal{C}_I), \\ \text{branch}: \quad & G_t = \text{Branch}(O_t,H_t,M_t), \quad A_t = \pi_{\text{main}}(O_t,H_t,\mathcal{C}_I,G_t). \end{aligned}\]

这里 $O_t$ 是当前视觉观测，$H_t$ 是短历史，$M_t \in \mathcal{C}_I$ 是当前选择咨询的 skill，$G_t$ 是 branch 返回的压缩指导信号。关键点在于: branch 不直接替主 agent 执行动作，而是输出结构化 guidance，再由主 agent 结合实时画面决定最终动作。

branch 输出被写成:

\[G_t = (\text{applicable}_t,\text{subgoal}_t,\text{plan}_t,\text{do\_not\_do}_t,\text{verify}_t)\]

这 5 个字段分别对应:

  • 当前 skill 是否适用
  • 当前局部子目标是什么
  • skill-conditioned 计划是什么
  • 当前不该做什么
  • 如何验证已经完成

这比简单把一段长 procedure 塞回主上下文更像“受控中间推理接口”。

实验与结论

作者在 4 个 visual-agent benchmark 上评测:

  • OSWorld: Ubuntu GUI agent benchmark
  • macOSWorld: macOS GUI benchmark
  • VAB-Minecraft: VisualAgentBench 中的 Minecraft 子集
  • Super Mario Bros: LMGame-Bench 中的游戏环境

比较的条件主要有 3 种:

  • No skill
  • Text-only skill
  • MMSkills

其中 text-only skill 也使用 branch 机制，只是没有 state cards 和 images。这个设置很关键，因为它说明“branch loading 本身”也是一个可分离的贡献点。

模型方面覆盖了较强和较弱的多模态模型，包括:

  • Gemini 3.1 Pro
  • Gemini 3 Flash
  • Qwen3-VL-235B-A22B-Thinking
  • GLM-5V-Turbo
  • Kimi-K2.6
  • Qwen3-VL-8B-Instruct

GUI 设置里，OSWorld 和 macOSWorld 的最大交互预算都是 20 步。所有 skill 都只从 non-test trajectories 提取，避免测试集污染。

下面先给出最关键的主结果表。OSWorld 上，MMSkills 对所有模型家族都带来整体提升。

Base modelNo skillText-onlyMMSkills
Gemini 3.1 Pro44.0840.7650.11
Gemini 3 Flash36.6540.2747.97
Qwen3-VL-235B21.3428.5739.17
GLM-5V28.7136.6138.51
Kimi-K2.634.9839.6646.59
Qwen3-VL-8B-Instruct10.7814.9325.40

可以看到两个很重要的现象:

  • MMSkills 基本稳定优于 No skill
  • Text-only skill 虽然有时也有帮助，但远不如 MMSkills 稳定

特别是较弱模型增益更大。比如 Qwen3-VL-8B-Instruct 在 OSWorld 上从 10.78 提升到 25.40，说明外部多模态 procedural knowledge 确实能补足弱模型自身的内部先验不足。

价值、局限与启发

这篇文章虽然很强，但仍有几个明显局限。

如果把这篇工作放回你现在的 agent 方向阅读脉络里，我觉得最有用的启发有 4 个。

  • 可以把 agent skill 从纯文本模板升级为 procedure + state card + visual cue 的结构。
  • 如果你后面做 GUI/code-use/desktop 类型 agent，when_not_to_use 和 verification_cue 两个字段非常值得保留，它们能显著减少误调用和错误完成判断。
  • branch loading 这个思想可以迁移到别的外部模块上，不只是 skill。比如 memory、tool docs、UI exemplars 也可以先在 branch 中阅读，再把 distilled guidance 回传主链。
  • 如果你后面想做 reward 或 verifier 设计，文章里的 before/after 视图和 verification_cue 很适合转成局部状态判别器或图像级判分信号。

这篇论文最核心的贡献，是把 visual agent 的 skill 从“文本步骤”升级成“带有状态判别与多视角视觉证据的多模态 procedure package”，再通过 branch loading 避免上下文污染，让这些 skill 真正在 GUI 和游戏环境里变成可调用、可验证、可迁移的外部知识单元。
