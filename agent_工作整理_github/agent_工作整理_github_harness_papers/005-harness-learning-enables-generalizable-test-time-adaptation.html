核心思想：学会改流程，把新任务的反馈变成程序改进

训练一个 proposer，读取任务描述、当前 harness 与执行报告，提出能实际提高得分的代码修改。测试时两个模型的权重都冻结，利用新任务的开发反馈多轮改写外部程序，再将选好的程序用于未参与适配的题目。

Harness 是组织模型调用、工具使用和信息传递的可执行程序。本文让 proposer 负责修改程序，solver 负责按程序解题；训练只更新 proposer。它学习的不只是答案或一句更好的 prompt，还包括何时增加解释器、如何保留证据、怎样安排检索和验证。

这里的 task 是一个 Reasoning Gym 题目家族，或一个多跳 QA benchmark。一份程序需要对同类的多道题有用。它与 JIT/Turbo 的每题专属程序不同：先用一批带评分反馈的开发题调好流程，再服务该任务中的新题。测试时不更新模型参数，但仍使用新域的答案标签和评分信号。

适配框架：执行当前程序，诊断失败，评估候选，再进入下一轮

先区分三份题集

题集用途QA 的一轮配置
$Q^{\mathrm{fb}}$：反馈题运行父程序，生成诊断报告供 proposer 阅读6 题，报告含答案与支持文档信息
$Q^{\mathrm{score}}$：评分题运行候选，形成训练奖励或选择分数64 题，与本轮反馈题不重叠
$Q^{\mathrm{eval}}$：留出题测量适配后的泛化，不用于选择程序约 300 题，与适配题分离

报告题让 proposer 看见失败原因，另取评分题要求修改也能帮助其他题。留出题再检验它是否泛化。QA 的开发题可跨轮复用；Reasoning Gym 测试适配则用同一份开发题产生反馈和选择，最终留出题仍独立。论文中的评分函数是：

\[J(h;Q)=\frac{1}{|Q|}\sum_{q\in Q}\operatorname{score}(h,q).\tag{1}\]

$h$ 表示 harness，$Q$ 为题集，$\operatorname{score}$ 是外部 grader 对每道题的分数；QA 使用答案 Exact Match（EM）。评分题虽然不直接作为题目文本进入 proposer 输入，仍通过奖励或候选选择影响适配。

一轮修改的输入与输出

\[\begin{aligned}x_t&=(\text{任务描述},h_{t-1},\text{执行报告}),\\y_i&\sim\pi_\theta(\cdot\mid x_t),\quad i=1,\ldots,G,\\h'_i&=\operatorname{Apply}(h_{t-1},y_i),\\h_t&=\operatorname{Select}(h_{t-1},\{h'_i\}_{i=1}^{G};Q_t^{\mathrm{score}}).\end{aligned}\tag{2}\]

$x_t$ 是第 $t$ 轮的修改上下文，$\pi_\theta$ 是 proposer，$y_i$ 是第 $i$ 个修改响应，$h'_i$ 是应用后的候选，$G$ 为候选数。选定 $h_t$ 后，重新运行反馈题并准备下一轮报告。接口检查、解析或执行失败会影响候选有效性。

  • Reasoning Gym：每轮 $G=1$，最多五轮；只有开发分严格提高才采用，否则保留父程序。输出采用 SEARCH/REPLACE 等结构化修改，并保持求解入口。
  • 多跳 QA：每轮 $G=8$，共十轮、四次独立 runs；选择最高分的有效候选，即使低于父程序也继续前进，全部失败才保留父程序。输出是诊断加不超过 200 行、定义 run 的 Python 程序。

因此 QA 的迭代不保证逐轮提升。Proposer 读取外部准备的报告再提交修改，也没有自主查看文件、运行调试工具的完整调查回路。

训练核心：让可运行、解题更好的修改获得更高概率

同一上下文采样多个修改，用冻结 solver 执行各候选，再按组内相对得分做 GRPO。总体希望最终程序在留出题表现更好，实际训练却对当前一次修改给即时奖励：

\[\begin{aligned}r_i&=J(h'_i;Q^{\mathrm{score}})+v_i,\\\widehat A_i&=\frac{r_i-\operatorname{mean}_j(r_j)}{\operatorname{std}_j(r_j)+\delta}.\end{aligned}\tag{3}\]

$v_i$ 是合法性附加奖励，$\widehat A_i$ 是组内标准化优势，$\delta$ 防止分母为零。一个修改响应的 token 共用该候选的优势；执行结果提供奖励，不需要穿过 solver、检索或代码环境反向传播。组内正优势只表示比其他候选好，不保证超过父程序。

Single-step / Multistep 的区别主要是训练见到的父程序分布。多步训练将前面选出的程序及新报告作为后续输入，仍按式（3）给当前修改奖励；没有把第十轮收益完整归因到第一轮。单步训练的 proposer 也可以在测试时连续修改，论文并未证明必须做多步训练才能多轮适配。

具体学到了什么：修复检索与作答之间的信息瓶颈

初始 QA 程序先检索、摘要，用摘要构造第二跳 query，最终也只读摘要作答。如果原文找到了答案，摘要却删掉关键实体或限定条件，后面再强的回答模型也无法恢复丢失信息。

  • 证据路径改写：摘要仍负责规划下一跳检索，但最终回答读取原始段落。它把“方便继续搜”和“保留答题细节”分成两种上下文用途。
  • 增加第三跳：解除固定两跳的限制，补找缺失关系；但额外调用也可能只增加成本和噪声。
  • 草稿触发验证：先写草稿，若草稿未在证据中出现，就用草稿再检索。这是生成程序内的条件分支；字面命中不等于事实支持，未命中也不等于错误。

Reasoning Gym 多数修改转向 Python interpreter loop。添加正确的 BFS、回溯或筛法仍可能因题目解析、工具协议、结果抽取失败而无益；额外工具组合奖励没有一致优于基础 RL。论文展示了上述 QA 程序实例，没有逐项隔离其因果贡献。

新域中，训练 proposer 的多轮平均最终结果甚至超过 80 个独立修改的 oracle 最好值，支持继承程序、利用更新反馈积累有效结构。但两种方案的父本、报告和筛选协议不同，不能单独归因于“新反馈”或推出严格算力效率优势。

Multistep RL 不一致优于 Single-step RL。Reasoning Gym 的五轮适配扩展实验中，格式变化题上两者均值分别为 0.649 与 0.725（每格式 24 个 seen/unseen 家族）；QA 也随数据集而异。后续状态训练有时有益，并不是通用保证。

成本与边界：适合任务级摊销，需要可评分的开发反馈

QA 一条适配 run 有十轮，每轮八个候选，每个候选回答 64 道评分题。假设全部有效且完成执行，名义评分工作量为：

\[\begin{aligned}N_{\text{候选—题目}}&=10\times8\times64=5120\quad\text{（一条 run）},\\N_{\text{四条 runs}}&=4\times5120=20480.\end{aligned}\tag{4}\]

这是题目执行次数，不是 LLM 调用次数；每次解题还可调用 solver 和检索各最多 12 次，此外还有反馈题运行与修改生成。无测试时反传也不代表便宜。论文没有完整的美元成本或端到端耗时对比；适配成本的合理用途是由后续同域 query 摊销。

  • 监督来源：开发答案和 grader 可用于适配，最终留出题不能参与选择。协议独立不等于无标签；开发集跨轮复用仍可能选择过拟合。
  • 长期归因：即时奖励没有解决“先退一步、后面获益”的多轮信用分配。合法性奖励还可能在答题全错时为正，应与正确率分开看。
  • 评测范围：部分家族被排除或按此前结果选取，oracle 使用留出得分；不应概括为任意新域都能获益。
  • 实现状态：笔记在 2026-10-12 核验仓库提交 5d095ef，README 为 “Code coming soon!”，未发现公开训练/推理实现。本页沿用该核验记录，不声称已运行作者代码。

核心结论：程序修改能力可以通过执行奖励训练，并迁移到未见题型与 QA benchmark；单步训练的编辑器也能连续适配。实验更有力地支持“减少坏修改、持续修复流程”，尚未证明总体超过强固定 harness，或多步训练必然更好。

对 search harness 最具体的启发，是分别设计“下一步检索上下文”“最终回答上下文”“是否继续搜”的可修改接口，定位信息在哪个环节丢失。若目标是同一 query 执行到一半改代码并续跑，还需要额外的证据、预算和状态迁移协议；本文反馈来自已执行的一批题，未提供这种热更新实现。
