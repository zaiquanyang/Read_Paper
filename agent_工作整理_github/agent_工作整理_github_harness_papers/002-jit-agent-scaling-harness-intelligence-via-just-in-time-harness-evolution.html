核心想法

JIT-Agent 学习的是“如何为当前任务写 harness”的生成器。面对研究、购物、旅行或文档处理等不同任务，模型可以生成不同的记忆结构、计划逻辑、工具暴露方式和执行控制，而不是所有任务共用一个固定 ReAct 外壳。生成出的程序围绕冻结的执行模型运行；部署时更新的是 harness 设计和跨任务经验库，不是模型权重。

  • 按题定制：任务结构决定程序结构，例如身份识别使用候选人—线索证据表，产品生成使用带依赖的 DAG。
  • 可执行接口：生成结果被拆成 memory、planning、action、capability orchestration（决定本步可用工具与 skills）四个模块，并由共享 kernel 执行。
  • 训练目标：同时追求任务奖励、低延迟和低成本；Stage II 学局部修复，Stage III 让候选超越历史 harness 档案。

Harness 协议：生成器输出什么

论文将 harness 表示为四元组 $h=(M,P,A,F)$。其中 $t$ 表示执行步，$s_t$ 是可变控制状态，$\xi_{\lt t}$ 是保留的事件历史，$\tau$ 是当前任务，$\mathcal C_\tau$ 是任务可用的工具与 skills。$v_t$ 是本轮记忆视图，$d_t$ 是局部指令，$\mathcal C_t$ 是本轮开放的能力集合，$e_t$ 是新产生的事件。一次执行的依赖顺序是 $M\rightarrow P\rightarrow F\rightarrow A$：

\[\begin{aligned}v_t&=M(\xi_{\lt t},s_t),\\d_t&=P(\tau,s_t,v_t),\\\mathcal C_t&=F(\mathcal C_\tau,s_t,v_t,d_t),\\(s_{t+1},e_t)&=A(s_t,\tau,v_t,d_t,\mathcal C_t).\end{aligned}\tag{1}\]
  • $M$ 决定当前轮向模型呈现哪些历史：全文、摘要、检索片段或结构化证据。
  • $P$ 根据轨迹和状态产生局部计划；没有显式规划器时可返回空指令。
  • $F$ 根据当前证据决定暴露哪些工具和 skills，必要时暂时隐藏 final answer。
  • $A$ 发出工具动作或终止答案并更新状态；kernel 负责真正执行和追加事件。

公开实现输出 memory.py、planning.py、action.py、tool_policy.py 和 prompt.yaml。最后一个是配置文件，不应误解为第五个论文模块。协议还区分“模型看到的压缩视图”和完整历史 $\xi_{\lt t}$，因此压缩上下文不会自动删除原始证据。

三阶段训练：从可运行到超越历史设计

Stage I · 学会按任务生成可执行 Harness

教师读取任务、协议、工具注册表和同类型种子设计，生成候选程序；通过接口检查与执行检查后形成 SFT 数据，再用偏好训练倾向于高奖励、低延迟、低成本的程序。记 $r$ 为任务奖励、$\ell$ 为延迟、$\kappa$ 为成本；$+$ 与 $-$ 分别表示偏好和非偏好候选。偏好关系要求：

\[h^+\succ h^-\iff r^+>r^-\land\ell^+\leq\ell^-\land\kappa^+\leq\kappa^-\land(\ell^+<\ell^-\lor\kappa^+<\kappa^-).\tag{2}\]

也就是说，候选要先在任务奖励上更好，同时不能让延迟和成本变差，并且至少有一项效率指标严格改善。

Stage II · 学会短程修复

将编译错误、接口不匹配、工具调用失败和运行异常与失败程序配对，教师提出补丁并验证。学生看到完整的“程序—诊断—修改”历史；只保留两轮内修复成功的轨迹，因此它覆盖的是局部可恢复错误，不等于拥有任意程序调试能力。

Stage III · Evo-GDPO 奖励超越历史

从 harness bank（记录程序及其评估结果的经验库）检索当前任务的参考设计，取其中最高奖励者作为 incumbent（当前参考设计）；同一任务生成多个 candidate（候选设计）。候选若超过历史 reward，获得额外演化奖励；只有不牺牲 reward 时，延迟和成本改善才会激活：

\[\begin{aligned}R_i^{\mathrm{rew}}&=r_i+\lambda_{\mathrm{evo}}[r_i-b_r]_+,\\R_i^{\mathrm{lat}}&=\mathbf1[r_i\ge b_r][b_\ell-\bar\ell_i]_+,\\R_i^{\mathrm{cost}}&=\mathbf1[r_i\ge b_r][b_\kappa-\bar\kappa_i]_+ .\end{aligned}\tag{3}\]

这里 $r_i$ 是候选任务奖励，$\bar\ell_i$ 和 $\bar\kappa_i$ 是候选延迟与成本统计，$b_r,b_\ell,b_\kappa$ 是 incumbent 对应指标，$[x]_+=\max(x,0)$，$\lambda_{\mathrm{evo}}$ 控制超越历史奖励的强度。三个奖励通道分别在同题候选组内标准化，再加权成优势，避免把准确率、秒数和美元直接混成原始分数；任务奖励通道的权重大于两项效率权重之和。之后使用 clipped PPO 目标与相对冻结 Stage-II checkpoint 的 token-level KL 惩罚训练生成器。训练期间会同时更新参数与档案；部署时参数冻结。档案只保留达到历史最高任务奖励、且至少一个维度严格改善的候选。

推理流程：静态生成、有限修复、跨任务积累

Static JIT：默认独立生成三个 harness，按五文件接口门槛和 selector 选一个，之后执行被选中的程序。selector 可用生成 completion 的 summed log-probability，或让 judge 比较设计；它没有看任务执行得分，因此选择本身是独立瓶颈。正常结束但得分低，不会自动重新生成；只有运行抛异常时才允许有限 repair。

Streaming JIT：任务完成后将 reward、延迟和成本写入 harness bank，后续任务检索这些经验。它是跨任务的经验积累，不是当前 episode 中途把正在运行的源代码换掉；论文也明确不把环境反馈注入当前 rollout。Shopping、Travel、Office 的 streaming 实验报告了更高的累计准确率终点，但 bank 更新依赖可靠的任务反馈，不能据此推断现实开放任务中会无监督地持续改进。

动态状态 ≠ 动态改代码：生成出的 Gearbox、Pegboard、Mulligan 等 harness 可以在内部切换工具、重新规划或重做失败动作，但这些是程序预先写好的条件分支。真正中途替换 harness 还需要状态迁移、schema 兼容、未完成调用处理和回滚机制，文档不能据此声称已实现。

实验与结论

主实验覆盖 BC+（BrowseComp-Plus）、DSQA（DeepSearchQA）、xBench、AgentIF、PinchBench 以及 Shop、Travel、Office、Odyssey 九项任务。JIT + GLM-5.2 在 BC+、DSQA、xBench、AgentIF、PinchBench、Office、Odyssey 上取得完整主表中最高分；JIT + DeepSeek-V4-Flash 在 Shop 上最高。

以冻结 DeepSeek-V4-Flash 的控制实验为例，DSQA 上 JIT-Agent 相对 Claude Code：分数 79.6→85.1，token 用量 625K→400K，成本 0.088→0.066 USD；xBench 上为 75.0→82.0、559K→212K、0.079→0.039 USD。AgentIF 上 JIT 的分数 63.8 仍低于 Claude Code 的 66.9，因此不能把效率优势等同于每项性能都更高。

公开仓库没有提供可直接复现三阶段训练的 trainer、完整数据及配置，论文的总提升不能拆解为每个阶段都已被充分消融验证。

对 Harness 研究的启发与边界

核心 takeaway：JIT-Agent 把“怎样组织一次任务”从提示词技巧提升为可执行程序设计问题；最可迁移的设计是结构化证据、工具门控和可恢复状态，而不是某个固定模板。
  • 公开代码提供生成、选择、修复、运行时和种子 harness，但没有对应三阶段训练实现，复现需要自行补齐训练器。
  • 静态 JIT 与 streaming bank 解决的是按题生成和跨任务复用；它们不等于当前任务执行中动态替换 harness。
  • 真实部署还需核算生成、选择、修复和执行四部分成本；一次 meta 调用并不代表总成本很低。
