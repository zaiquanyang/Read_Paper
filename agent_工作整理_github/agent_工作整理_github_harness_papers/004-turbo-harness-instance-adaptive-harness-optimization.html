核心想法：强全局程序之上，再做一次实例适配

Turbo Harness 训练一个小型 editor，在任务执行之前，为当前实例修改全局 harness。Editor 读取任务、已优化的全局程序和历史编辑经验，输出补丁；补丁应用后，冻结的执行模型才开始解题。每题仅调用一次 editor，无需先收集本题失败轨迹再重跑。

Harness 是模型外的程序，负责上下文、状态、工具调用、控制循环和验证。全局优化寻找平均表现好的共同程序，但“先查 git 历史”“立即提交”“多做测试”等规则并不适合每道题。同时，全局搜索淘汰的候选可能包含只对某类题有效的策略。Turbo 把这些成功与失败记录压缩为 playbook（带适用条件的编辑经验册），学习什么时候应采用哪些改动。

与 JIT-Agent 生成完整四模块 harness 相比，Turbo 从同一个强全局程序出发，只改必要部分。训练时更新 editor，executor（真正调用工具解题的模型）保持冻结；测试时二者都冻结，变化发生在程序上。

三阶段框架：全局搜索 → 编辑经验 → 实例补丁

Stage A · 获得共同程序与搜索档案

Meta-Harness 外循环提出程序，内循环执行 agent 并评估，产生全局程序 $H^\star$ 与搜索档案 $\mathcal A$。档案保存候选源码、得分、工具输出、执行轨迹和失败。这个阶段追求训练任务平均表现：

\[H^\star\in\arg\max_{H\in\mathcal H}\mathbb E_{x\sim\mathcal T}\big[r(\operatorname{Agent}(M,H,x))\big].\tag{1}\]

$M$ 是冻结执行模型，$\mathcal H$ 是程序设计空间，$\mathcal T$ 是训练任务分布，$r$ 是执行结果的奖励。共同程序有效，并不意味着它对每个实例都最优。

Stage B · 将搜索副产品变成条件化经验

  1. Extraction：对每个训练实例整理不同程序的结果与轨迹，区分“有成功失败对比”“全部成功”“全部失败”；选择差异明显的版本，计算源码 diff。该步骤不调用模型。
  2. Reflection：强模型结合实例特征、代码差异与行为差异，提炼策略、适用条件、理由和置信度，过滤低置信度与已知坏模式。
  3. Curation：合并等价策略，累计 helpful / harmful 证据，净负面经验转成 anti-pattern（应避免的修改），删除过于模糊或只针对某题的条目。

经验区分 scaffold_modification（改控制流）与 text_injection（改提供给模型的信息）。训练和测试时整个固定 playbook 都进入上下文，不是另行训练检索器，也不是每完成一道测试题就更新经验库。不同版本的成败对比提供经验依据，但不等于完成了严格因果识别。

Stage C · 每题一次编辑，再执行

\[\begin{aligned}p_x&\sim\pi_\theta(\cdot\mid x,H^\star,\mathcal P),\\H_x&=H^\star\oplus p_x,\\\text{结果}&=\operatorname{Agent}(M,H_x,x).\end{aligned}\tag{2}\]

$\pi_\theta$ 是 Qwen3.5-9B editor，$\mathcal P$ 是经验册，$\oplus$ 表示应用代码修改，$H_x$ 是实例专用程序。每道题都从同一个 $H^\star$ 开始，不会继承上一道测试题的补丁。显式输出 NO_PATCH_NEEDED 时运行原程序；无法解析、应用或通过验证的补丁，在训练中得到零分且不执行环境。

训练对象是 Editor：奖励来自 Executor 的真实执行

训练为同一实例采样 $G$ 个补丁，分别应用、检查并调用冻结 executor，得到任务奖励。GRPO 根据同题候选的相对表现优化补丁 token 的概率。因此梯度更新的是“怎样改程序”，不是 executor 的“怎样修 issue”；训练仍需要大量环境 rollout。

奖励既考虑成功，也有任务相关 shaping

SWE 两项任务的奖励使用成功与执行步数，$s$ 为实际步骤，$L=40$ 为上限：

\[r=\begin{cases}1-\dfrac{s}{2L},&\text{任务成功},\\0,&\text{任务失败}.\end{cases}\tag{3}\]

ScienceWorld 使用环境得分除以 100；ALFWorld、DBBench、TB2.1 使用二元结果；WebShop 使用稠密得分，并对超过同题全局程序的非弃权补丁加 0.1。除 SWE 外五项任务的明确弃权减 0.05，并截断到非负。测试报告的指标不包含这些 shaping 项。

默认使用全参数 FSDP 训练，学习率 $10^{-6}$、KL 系数 $10^{-3}$，不同任务的 group size 为 8 或 16。可信 runner 在生成程序之外评分，禁止修改受保护的评分接口，避免 editor 通过改评分逻辑取得虚假奖励。

WebShop 的表注和奖励正文对特殊设置的措辞存在歧义，复现时应核对具体配置；不能把式（3）或标准二元奖励统一套到所有任务。

实例补丁究竟改了什么？

  • 定位策略：Jinja2 回归问题加入查看 git history 的流程，另一个 datetime 库问题没有加入相同步骤，说明不是给每题追加统一提示。
  • 阶段预算：Django 示例增加理解与修复阶段的步骤，取消立即提交；SymPy 示例只增加修复预算，仍保留一步提交。
  • 运行代码：Gunicorn 示例将验证门槛由 step 8 提前到 6，并扩展源码修改检测器，使其识别 echo ... >> ...py。

这些例子支持补丁空间同时包含提示与控制流代码。TB2.1 的强制工具调用案例来自训练任务上的外循环搜索，不能把它当作被保留的测试实例补丁；论文说明该 benchmark 的测试补丁没有保存。

动态性的边界：实例适配发生在执行前。生成后的程序可以运行条件分支，但论文没有实现正常 episode 中持续重新调用 editor、替换 harness 并迁移状态；“每题不同”不等于“运行中持续改代码”。

主要结果：同一全局底座上的实例编辑带来增益

最容易解释的对照是 Meta-Harness → Turbo：执行模型与全局底座相同，新增实例适配。其他方法可能失败后重跑、使用不同 runtime 或另做训练，不能据整张排名表单独归因 editor 算法优劣。

Terminal-Bench 2.1：55.5% 的测试通过率

使用 Claude Sonnet 4.5，在 44 道测试题上运行五次：Meta-Harness 为 50.5±1.7%，Turbo 为 55.5±1.4%（SEM），平均 turns 76.3→71.2，执行费用 1.56→1.38 USD/task。最强人工基线 Terminus-Kira 为 52.3±1.1%；但 OpenHands 费用仅 0.85 USD，因此 Turbo 并非所有维度都最优。

消融：小 Editor 需要训练才能利用经验

全局 Meta 底座为 50.7%；未训练 9B editor 无 playbook 为 51.3%，加 playbook 为 50.0%；训练但无 playbook 为 49.3%，训练且有 playbook 为 64.0%。这支持“编辑训练与经验库互补”，不支持“任意模型拿到经验库就会提升”。冻结 Sonnet + playbook 为 55.3%，Opus 为 61.3%，展示了将某项编辑能力训练进小模型的可能性。

误差条和重复运行衡量 executor 的执行随机性，没有覆盖重新训练 editor、重新生成补丁或重新划分数据的方差；四个交互任务仅报告一次测试运行。

结论与复现边界

核心贡献：把全局搜索中被丢弃的编辑经验重新利用起来，训练 editor 判断“当前题该对强共同程序做什么局部修改”。适配范围可以从提示文本延伸到验证时机、阶段预算和控制代码。
  • 相比每题重新搜索，测试只增加一次 editor 调用；离线搜索和训练成本仍真实存在。
  • 开源内容包含 SkyRL、GRPO 配置、训练脚本、split、全局程序与 playbook，是有实际训练实现的工作；核验版本为 44610b8。
  • 公开复现指南主要覆盖 SWE-smith、Verified、ALFWorld、TB2.1 四项，论文有七项。笔记未确认可直接下载的已训练 editor checkpoint，配置要求提供 ADVISOR_CKPT。
  • 未展示开放 Web search 主实验，WebShop 的受控商品环境不能代替开放网页检索；正常执行中再次编辑和状态迁移也仍是扩展方向。

本专题中，Video-RSI 离线演化可复用程序，JIT-Agent 按题生成完整程序，CoTrace 管理执行模型与 harness 交替更新的数据；Turbo 的定位是在强全局 harness 上，执行前一次性生成实例补丁。
