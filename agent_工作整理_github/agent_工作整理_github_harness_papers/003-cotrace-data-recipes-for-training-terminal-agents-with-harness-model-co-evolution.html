核心想法：轨迹必须带着 Runtime 来源进入训练

CoTrace 将 Terminal Agent 视为“模型参数 + 执行 harness”的联合系统。失败轨迹揭示运行时应该怎样改，经过验证且与当前 harness 匹配的成功轨迹才用于模型模仿；在线 RL 则直接在当前 harness 上采样。每次组件更新先单独评估，再决定接受或回滚，使轨迹生产、程序修改与模型训练形成可追踪的闭环。

Harness 是模型外面的执行程序：负责渲染提示、绑定工具、处理观察、控制步数、恢复错误及提交结果。同一条成功轨迹可能依赖某个候选 harness 的处理器；如果这个候选最终没有被采用，直接把轨迹拿来训练，就可能让模型学到部署时无法复现的流程。因此，CoTrace 的重点是什么数据进入哪一种优化、来自哪一个运行时，而不是简单增加成功轨迹数量。

协同演化：先改 Harness，再在采用的 Runtime 上训练

记 $\theta$ 为模型参数，$H$ 为 harness，$x$ 为任务，$\tau$ 为工具调用与观察交错组成的轨迹，$v_x$ 为任务验证器。二者共同决定运行结果：

\[\max_{\theta,H}J(\theta,H)=\mathbb E_{\substack{x\sim\mathcal T\\\tau\sim\pi(\cdot\mid\theta,H,x)}}[v_x(\tau)].\tag{1}\]

式（1）不是只优化 checkpoint；论文以交替更新近似求解：

\[\begin{aligned}H_{t+1}&\approx\arg\max_H J(\theta_t,H),\\\theta_{t+1}&\approx\arg\max_\theta J(\theta,H_{t+1}).\end{aligned}\tag{2}\]

这里 $t$ 是外层迭代轮次。式（2）描述优化方向，实际每轮还要经过Route、Ratchet、Refresh 三项控制：

  1. Route（轨迹分流）：将反复出现的运行时故障聚类，交给 meta-agent 提出 harness 修改；环境或评分器故障不当作模型失败。模型 SFT 则只接收经过验证、格式有效、与采用的 harness 匹配的成功示范。
  2. Ratchet（组件更新评估）：先固定模型比较候选 harness；接受后再固定 harness 比较候选模型。没有通过的组件保留旧版，避免将一次系统提升同时归因于两个变化。
  3. Refresh（任务刷新）：已掌握且已收集为训练样本的任务退出活跃 evolve set，再从未访问的 reservoir 补入新任务，让后续搜索和训练继续面对尚未解决的 frontier。

Promotion 是决定是否换版本的关卡

Incumbent 是当前采用的版本，candidate 是尚待检验的候选；promotion split 是固定的 102 道评估题，与搜索和训练题分离。记 $w$ 为候选新解决的任务数，$\ell$ 为候选新破坏的任务数，主要接受条件为：

\[w>\ell\quad\Longleftrightarrow\quad\text{新解决任务数}>\text{新破坏任务数}.\tag{3}\]

例如，候选多解决 4 题、却让旧版已解决的 1 题失败，净收益为 3，满足式（3）；这不保证每道旧题都不退步。原文另允许 $w=\ell$ 的 clean tie：评估完整，且没有容器或基础设施异常；并非所有平局都可接受。被否决的候选回滚，其轨迹仍保留来源记录，但不会自动成为当前模型的标准训练数据。

什么时候将任务移出训练前沿？

\[\begin{aligned}\mathcal M_t&=\{x\in\mathcal E_t:\mathrm{solved}_t(x)\land\mathrm{harvested}_t(x)\},\\\mathcal E_{t+1}&=(\mathcal E_t\setminus\mathcal M_t)\cup\mathrm{Refill}(\mathcal T_{\mathrm{pool}}).\end{aligned}\tag{4}\]

$\mathcal E_t$ 是当前活跃任务集，$\mathcal M_t$ 是可以退休的任务，$\mathcal T_{\mathrm{pool}}$ 是补充任务池。SFT 中，solved 表示当前系统已验证成功，harvested 表示成功轨迹已选入训练语料；仅偶然成功一次但没有收集为可用样本，不能直接退休。在线 RL 不维护持久的 SFT 语料，原文以行为成功决定任务退休，不能把 SFT 的语料条件机械套到 RL。

数据配方：匹配的是运行语义，不只是版本名

每条轨迹保存 provenance（来源记录）。其中 fingerprint $\phi(\tau)$ 是 prompt template、工具绑定和 observation processors 的语义哈希签名；另外记录任务实例、结果、失败类型与验证证据。CoTrace-SFT 的来源匹配要求：

\[\tau\text{ 可作为匹配示范}\ \Longrightarrow\ \phi(\tau)=\phi(H_{\mathrm{adopted}}).\tag{5}\]

式（5）只是筛选条件的一部分，还要检查成功与格式、任务覆盖和重复度。SFT 优先采用当前成功轨迹，限制每任务样本数和历史重放；覆盖不足时，在已采用的 harness 下重新生成 fresh rollout，并为示范配置相应系统提示。

配方轨迹来源核心区别
All-evolve汇总 harness 搜索产生的成功可能来自多个候选 runtime，不强制匹配当前 harness。
Mixed siblings混合兄弟候选 harness 的成功检验大量混合示范是否能产生可接受的模型更新。
CoTrace-SFTfingerprint 匹配的成功 + fresh top-up运行时对齐，并控制每任务采样、历史比例与覆盖。
CoTrace-RL已采用 harness 上的在线交互以当前运行时产生新轨迹与奖励，不构建离线示范库。

例如，旧候选的处理器自动修复了工具参数，成功轨迹可能默认这一能力存在；部署 harness 若没有该处理器，模型模仿同样动作仍可能失败。来源记录帮助识别这种依赖。它并不证明所有 unmatched data 都有害：论文的 sequential all-evolve 对照也取得模型增益；CoTrace-SFT 又同时改变了匹配、提示条件、新鲜度和采样上限，不能将全部收益归因于单一 fingerprint。

实现重点：改执行控制，验证环境契约

Harness Search 怎样产生候选

HarnessX 用 typed config 表示可编辑的运行程序。搜索采用两代 tournament：先提出 5 个候选，再从表现最好的版本派生第二批 5 个；固定模型，在 evolve set 上筛选，再把选中的候选送入 promotion。检查覆盖结构合法性、预期影响、小规模 probe 和运行约束；每次修改必须写明失败簇、因果假设、精确 patch、影响任务及回滚条件。

被接受改动的主要类型是 loop/repeat breaker（53%）、step budget 与 self-verify（26%）、verifier dependency guard（21%），没有新增工具。它们分别处理反复循环、如何分配步骤并自检、以及保护验证器依赖。作者设置中的收益更多来自执行控制与验证防护，不是工具数量增长。

SFT 与 RL 各自更新什么

SFT 使用 LoRA 学习匹配运行时的成功示范。RL 使用 DPPO，以任务完成的二元 reward 计算 group-relative advantage：每个 prompt 采样 8 条，丢弃奖励无差异的 zero-variance group 并主动补采样；使用 binary TV trust region $\delta=0.1$ 和 reference KL 系数 $\beta=0.01$。每个 stage 为 2,304 episodes，单 agent 最多 40 steps。

论文记录过“初始 reward 全为 0”的工程故障：reset 丢失任务实例渲染、user turn 使用错误模板、system override 覆盖 submission action、working directory 不正确。修复提示 schema 和目录后奖励恢复。对 Terminal Agent 而言，奖励为零也可能是环境和运行时契约出了错，应先核对这些环节，再判断 policy 是否缺乏能力。

跨 Runtime 迁移：Checkpoint 应与 Harness 一起评估

Terminal-Bench 2.1：在 baseline harness、89 道题的三次独立试验中，Base、SFT、RL 平均解题数为 18.7、18.3、19.7；对应 pass@1 约为 21.0%、20.6%、22.1%，pass@3 为 30.3%、29.2%、33.7%。SFT 与 Base 接近，RL 的小幅差距也在试验波动范围内，不能将 Tmax 的 +10 / +12 直接解释成跨域稳定增益。

结论与边界

最值得借鉴的是数据与评估的管理规则：每条轨迹知道由什么 runtime 产生、为什么被选择；每次更新知道哪个组件被固定；每道任务知道是否已成功、是否已产生可用训练信号。模型与 harness 应作为联合部署单元评估。
  • Promotion 题用于反复选择组件，88 / 90 不是独立测试集上的无偏泛化估计；固定另一组件也不消除评估噪声。
  • 102 题评估通常波动约 ±2 题、最坏约 5 题；多数 co-evolution chain 为单次运行，不能只凭小幅差距下强结论。
  • SFT 配方同时改变多个因素，SFT 与 RL 的算力也不相同；收益无法归因于单独的 fingerprint 或单独的 loss。
  • 结论主要来自 Qwen3.5 两个规模与 Tmax，后期课程会趋于饱和；harness search 使用 proprietary meta-agent，完整复现还需补齐这部分。

与本专题其他工作相比，Video-RSI 主要演化冻结模型外的程序，JIT-Agent 训练按题生成程序的模型；CoTrace 则管理执行模型与 harness 交替更新时的数据流。三者关注的学习对象不同，不能把“harness evolution”理解为同一种训练流程。
