Contexts are Never Long Enough: Structured Reasoning for Scalable Question Answering over Long Document Sets

问题与动机

长文档、多文档问答在金融、法律、科研分析等场景非常常见，但即便前沿模型已经支持百万 token 上下文，真实文档集合依然会很快超出上下文窗口。常见做法是：

  • 把文档切成 chunk。
  • 在 chunk 上分别抽取或回答。
  • 再把 chunk 级结果聚合成最终答案。

作者认为这里有一个根本性问题，称为 aggregation bottleneck：

  • chunking 虽然缓解了“放不进上下文”的问题；
  • 但随着 chunk 数量增多，系统仍然需要对越来越多的 chunk 级中间结果做二次聚合与推理；
  • 这其实又把问题重新变回了“长上下文整合问题”。

也就是说，很多 long-context 方法并没有真正摆脱长度瓶颈，只是把瓶颈从“原始文档”转移到了“chunk 输出的聚合层”。

这张图对应论文最重要的动机：

  • 传统 chunk-based pipeline 把原文切碎后，虽然局部处理更容易；
  • 但下游还是要把大量局部结果重新拼起来；
  • 随着文档数和 chunk 数上涨，聚合层的负担会迅速膨胀；
  • SLIDERS 的做法是把这些局部信息沉淀到结构化表中，让后续推理在数据库上进行，而不是继续在文本上“拼接后再读”。

“aggregation bottleneck” 这个概念很强，因为它解释了为什么很多方法在工程上看似做了分治，实质上仍然没有解决可扩展推理。

当问题需要强主观判断、模糊语义解释、开放式写作时，数据库表示未必能完整承载所有信息。

方法核心

作者的核心判断是：

  • 真正需要扩展的不是一次性喂给模型的文本长度；
  • 而是系统持久化、组织、查询和整合证据的能力。

所以他们把任务从：

  • “让 LLM 在超长文本里直接找答案”

改写成：

  • “让 LLM 先把文本转换成结构化数据库，再在数据库上做程序化推理”。

这意味着：

  • 文本负责提供原始证据；
  • 关系数据库负责保存显式状态；
  • SQL 负责执行聚合、过滤、比较、算术与跨文档整合；
  • LLM 更像一个 agent，负责 schema 设计、抽取、纠错、查询生成与多轮工具调用。

作者把整个方法拆成五个任务，这也是论文最值得关注的地方。

作者比较了：

  • RAG
  • LongRAG
  • GraphRAG
  • 直接使用 frontier LLM
  • DocETL
  • Chain of Agents
  • RLM
  • SLIDERS

这使得论文不仅和传统检索问答比，也和更偏 agent / decomposition / scaffold 的系统比。

SLIDERS 用 Qwen3.5 122B-A10B 做底座时，context-bounded benchmark 平均也能达到 75.26，显著高于直接把同一模型当 basemodel 使用时的 61.44。

这表明收益主要来自 框架设计，而不是单靠更强闭源模型。

论文给出的结论是：

  • 相比 GPT-4.1 直接读长上下文，SLIDERS 平均高 6.6 个点；
  • 在 Oolong 这种聚合压力大的任务上，结构化推理优势尤其明显。

这说明作者抓住的不是单纯“上下文不够长”的问题，而是“跨片段聚合、比较、算术、全局一致性维护”本来就不适合纯 free-form 文本推理。

价值、局限与启发

我认为这篇工作的主要贡献可以概括为 4 点：

  • 提出 aggregation bottleneck 这一问题表述

很多 long-context/chunk-based 方法的真正瓶颈被说清楚了。

  • 提出 SLIDERS 这一结构化推理框架

把长文档问答改写为数据库构建与 SQL 推理问题。

  • 把 reconciliation 做成系统核心模块

尤其强调 provenance、rationale、metadata 在全局一致化中的作用。

  • 构建 ultra-long benchmark

WikiCeleb100 和 FinQ100 让论文真正评到了现有 context window 之外。

相比把中间结果保留成摘要文本、scratchpad 或递归 prompt，数据库是一种更稳定、更可计算、更可审计的状态表示。
