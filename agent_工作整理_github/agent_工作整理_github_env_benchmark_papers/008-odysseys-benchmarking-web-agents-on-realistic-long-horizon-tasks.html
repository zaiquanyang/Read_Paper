实验与结论

将 Opus 4.6 的步数预算从 100 扩展到 200：

  • 完全成功率从 44.5% 提升至 76.5%（86/200 → 153/200），单调持续上升（100 步 44.5% → 120 步 50.5% → 150 步 59.5% → 180 步 67.0% → 200 步 76.5%）
  • 14.5% 的任务即使 200 步也耗尽预算
  • 乐观上界估计约 86.0%——至少 ~14% 的任务即使无限步也失败
  • 轨迹效率从 100 步的 1.06% 变为 200 步的 1.08%，表明性能未退化，Agent 仍在做有效工作
  • 在 76 个 hard 任务子集上，Opus 从 10% 升至 65%（+55pp），而 Qwen 3.5-9B 在 100→200 步间几乎无提升（1.3% flatline）——Qwen 失败表现为在标签页间无序跳转（thrashing），是能力上限而非步数限制

价值、局限与启发

  • 成本高昂：Opus 4.6 每个任务约 30 分钟 + $2.5，完整评估 200 任务约 $500+
  • 评估依赖 LLM judge：虽然 rubric 一致性高，但仍受 judge 模型能力限制
  • 仅限 Web 浏览：任务围绕 Chrome 浏览器，未覆盖桌面应用、移动端等更广的 computer-use 场景
  • 偏重信息获取型任务：主要为搜索、比较、汇总，对交互型任务（如填写表单、在线购物）覆盖有限
  • 静态基准：Web 内容随时变化，任务可行性可能随时间退化
  • 开源模型评估不完整：仅测试了 Qwen3.5 和 UI-TARS，未覆盖更多开源 computer-use 模型
  • RL 训练信号：Rubric 提供的细粒度部分信用信号可用于强化学习训练弱模型，这是论文明确指出的方向
  • 子 Agent / 多 Agent 架构：高扇出任务（10-30 子项）需要子 Agent 分工协作
  • 步数感知规划：Agent 应推理剩余步数预算，在信息收集与产出生成间动态切换
  • 多动作批处理：GPT-5.4 每次调用返回 2.03 个动作（vs Opus 的 1 个），显著减少 wall-clock time——训练或 prompting 策略可显式鼓励此行为
  • 跨模态扩展：将长程评估从 Web 扩展到桌面 OS、移动端等更广泛的 computer-use 场景
  • 动态基准维护：Web 内容变化导致任务失效，需要自动化可行性检测和任务更新机制
