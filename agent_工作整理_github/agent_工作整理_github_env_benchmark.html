Agent World Model: Infinity Synthetic Environments for Agentic Reinforcement Learning

agent arXiv abs PDF Code arXiv 2602.10090
核心思想：这篇工作提出了一个很有分量的 agent 基础设施方向：用数据库与代码驱动的大规模 synthetic environments 来支撑 agentic RL。它最有价值的不只是“合成了 1,000 个环境”，而是把 environment synthesis、verification-based reward、history-aware training 和大规模并发 agent RL 串成了一条完整 pipeline，对后续 agent 训练平台的设计很有参考意义。

问题与动机

作者提出的问题很明确：

  • 现有 agent benchmark 数量太少，难以支撑大规模 RL。
  • 使用真实 API 或真实网站进行训练，成本高且不稳定。
  • 让 LLM 充当“环境模拟器”虽然灵活，但会在状态转移、工具返回、环境一致性上产生 hallucination。
  • 大多数 agent synthetic data 工作更偏 task synthesis 或 trajectory synthesis，而不是 environment synthesis。

所以这篇论文试图补的空白是：

能否从零开始，自动生成大量“可执行、状态一致、支持工具交互、支持 reward 验证”的 agent 环境？

作者给出的答案是：可以，而且要用更像真实软件系统的方式做，也就是：

  • 数据库管理状态
  • MCP 接口暴露工具
  • 代码驱动状态转移
  • verification code + LLM judge 生成可靠 reward

方法核心

AWM 的核心思想是：一个 agent 环境本质上都可以拆成三层：

  • State backend：环境状态存在哪里，如何持久化。
  • Tool interface layer：agent 通过什么工具观察和操作环境。
  • Task-specific success criteria：任务完成与否如何判断。

作者把环境 synthesis 分解成多个可控步骤：

  • scenario generation
  • task generation
  • database synthesis
  • sample data synthesis
  • toolset schema synthesis
  • MCP environment code synthesis
  • verification code synthesis

这样做的好处是，每一步都有明确输入输出，也更容易自动校验和自修复。

实验与结论

作者选用 Qwen3 thinking models 的 4B、8B、14B 作为 base agents，在 526 个环境、3,315 个任务上训练。

关键训练配置包括：

  • 最多 96 个 optimization steps
  • learning rate 为 $7\times 10^{-7}$
  • batch size 64
  • 16 rollouts
  • 每步并发 1,024 个 isolated environment instances
  • sliding window size $w=3$
  • 最大交互轮数 20

评测 benchmark 是三套完全 OOD 的 tool-use benchmark：

  • verified $\tau^2$-bench
  • BFCLv3
  • MCP-Universe

这点很重要，因为作者强调训练环境并不是针对测试 benchmark 定制的。

在 $\tau^2$-bench 上，EnvScaler 某些设置仍然更强。这说明 environment quantity 不是唯一变量，environment distribution 和 benchmark overlap 也在起作用。

价值、局限与启发

这篇工作也有一些明显局限。

如果从 agent 研究视角总结，这篇 paper 最值得带走的经验是：

  • 想做 agentic RL，训练环境是第一性问题，不能只盯着 policy algorithm。
  • 可执行 environment 比 LLM-simulated environment 更适合做稳定 RL。
  • reward 应尽量 grounded 到 state，而不是只看自然语言 trajectory。
  • protocol correctness、history management 这些工程细节，实际上都值得进入训练目标。
  • environment synthesis pipeline 本身可以成为 agent 基础设施的一部分，而不是 benchmark 附属物。

Meta-Harness: End-to-End Optimization of Model Harnesses

agent arXiv abs PDF arXiv 2603.28052
核心思想：附录最后给了不少非常实用的经验，我觉得值得记：

问题与动机

很多人默认“harness 很重要”，但仍把它当工程经验；这篇则把它形式化成了明确的 outer-loop search problem。

方法核心

整体流程如下图所示。

外层循环非常简单：

  • proposer 读取 filesystem 中所有历史候选 harness 的代码、分数和执行日志；
  • proposer 写出新的 harness 候选；
  • 系统评估这个 harness；
  • 把新代码、得分和执行轨迹再写回 filesystem；
  • 重复迭代。

注意这里最关键的点不是“做了 evolution”，而是 proposer 有能力主动浏览一个持续增长的经验库，而不是被动吃一段预先压缩好的 prompt。

Meta-Harness 和很多 optimizer 最本质的区别不是有没有 Pareto frontier，也不是有没有 population，而是：

  • 它把完整历史暴露给 proposer；
  • proposer 可以跨很多旧候选去看原始代码和 execution trace；
  • proposer 不必局限于某个 parent，也不必只看最近一步。

附录里给了一个很有说服力的统计：

  • 在 TerminalBench-2 的一次搜索中，proposer 每轮中位数读取 82 个文件；
  • 其中 41% 是 prior harness source code；
  • 40% 是 execution traces；
  • 只有 6% 是 score/summary files。

这说明 proposer 并不是“装作能看 filesystem，实际上只在本地小修小补”，而是真的大量使用原始历史进行非马尔可夫式诊断。

作者刻意把 outer loop 设计得非常简洁，只保留：

  • population；
  • evaluation；
  • logging；
  • Pareto frontier。

它没有像很多方法那样手工设计：

  • parent selection heuristics；
  • mutation operator；
  • critique schema；
  • reflection template。

作者的观点是：这类控制结构越多，越像在把“如何诊断和改 harness”重新手工编码一次。Meta-Harness 反而把这些判断交给 proposer agent 自己做。

这背后的隐含立场很明确：

  • 如果 coding agent 足够强，外循环应尽量 minimal；
  • 真正重要的是让 agent 访问足够丰富的 raw experience；
  • agent 自己会学会怎样从这些经验里形成因果假设。

价值、局限与启发

如果把这篇放到 agent 主题下，我觉得它最重要的启发是：

  • agent 的提升不一定来自更强模型，也可以来自更强 harness；
  • harness 自身可以作为一等公民被自动搜索，而不是只能靠人手工写；
  • 对 agent system 来说，execution traces 往往比 summary 更值钱；
  • coding agent 不仅可以 solve task，也可以当 “system optimizer”，去反过来优化自己运行的那套外部程序；
  • 未来很可能出现“模型权重 + harness 代码 + memory 结构”一起 co-design / co-evolve 的范式。

附录最后给了不少非常实用的经验，我觉得值得记：

  • skill text 非常重要；
  • search set 要足够难，不然没东西可优化；
  • 日志要 machine-readable、便于 grep；
  • 最好提供小 CLI 帮 proposer 看历史；
  • full eval 前要做 lightweight validation。

这些建议都很 agent engineering，而不是纯理论。

这篇工作最大的价值，在于它把“代码级 agent harness 本身可以被自动搜索优化”这件事做成了一个可信、可执行、跨任务域的范式。它不是简单把 LLM 用来写 prompt，而是让 coding agent 真正通过 filesystem 访问原始经验，去做程序级别的诊断、归因和改写。

如果只记三句话，我会记：

  • harness 和 model weights 一样重要，甚至在某些 benchmark 上更重要；
  • 对 harness engineering 来说，execution traces 这种原始经验比压缩 summary 更关键；
  • 足够强的 coding agent，已经可以开始自动做 “system-level agent optimization” 了。

方法核心

本文提出核心问题：当前前沿语言模型能否可靠地从现实生活上下文中学习并解决基于这些上下文的任务？

引入 CL-bench Life——首个专注于日常生活场景的 context learning benchmark，包含 405 个人工策划的上下文-任务对和 5,348 个验证标准。

  • 每个 rubric 化为二值问题（仅允许 yes/no）
  • 使用 GPT-5.1（高推理强度）作为默认评估器
  • 严格标准：任务被认为成功解决当且仅当所有 rubrics 都通过
  • Rubrics 与上下文/任务解耦——评估时仅提供生成的解决方案和 rubrics
  • 人工验证 100 个样本确认评估准确率 >90%
  • 不同评估器的一致性：Cohen's κ 范围 0.710~0.773（实质性一致）

实验与结论

当前的 context learning benchmark 主要存在以下差距：

  • 专业领域偏向：CL-bench、CL4SE、OctoBench 等聚焦金融、科学、编程等专业场景，无法评估模型在日常生活情境中的上下文学习能力
  • 上下文过于"干净"：现有 benchmark 的上下文通常结构良好、逻辑清晰，而真实生活中的上下文往往混乱、碎片化、个性化
  • 端到端耦合：Agent benchmark（WebArena、SWE-bench 等）将多种能力耦合在一起，难以隔离评估 context learning 本身
  • 长上下文不等于好推理：长上下文 benchmark 主要测试信息检索能力，而非对混乱上下文的深层推理

每个实例由三部分组成：

  • Context（上下文）：自包含的现实生活场景信息（不需要外部检索）
  • Task（任务）：需要基于上下文推理才能解决的问题（不能仅靠预训练知识解决）
  • Rubrics（验证标准）：每个任务平均 13.2 个二值化验证标准（yes/no）

关键设计：

  • 全部由人工策划（每个实例平均 13 小时专家工作量）
  • 约 59.8% 的实例是多轮对话形式
  • 上下文自包含，解决任务不需要外部检索

价值、局限与启发

当前的 context learning benchmark 主要存在以下差距：

  • 专业领域偏向：CL-bench、CL4SE、OctoBench 等聚焦金融、科学、编程等专业场景，无法评估模型在日常生活情境中的上下文学习能力
  • 上下文过于"干净"：现有 benchmark 的上下文通常结构良好、逻辑清晰，而真实生活中的上下文往往混乱、碎片化、个性化
  • 端到端耦合：Agent benchmark（WebArena、SWE-bench 等）将多种能力耦合在一起，难以隔离评估 context learning 本身
  • 长上下文不等于好推理：长上下文 benchmark 主要测试信息检索能力，而非对混乱上下文的深层推理
  • 证据平衡与不确定性校准：过度投入单一叙事，面对多种合理解释时缺乏保留模糊性的能力
  • 隐含结构推断：依赖表面线索而非恢复底层关系（如权限结构、因果链）
  • 指令遵循与约束遵守：包含无关信息或违反任务要求
  • 细粒度推理与 grounding：在对齐细节和重建隐含逻辑方面存在困难
  • 首个专注于现实生活场景的 context learning benchmark：填补了现有 benchmark 在日常生活上下文评估方面的空白
  • 高质量人工策划数据：405 个实例、5,348 个验证标准，每个实例平均 13 小时专家工作量
  • 系统化的分类体系：三大类九子类覆盖日常生活中常见的上下文类型
  • 严谨的评估方法：二值化 rubrics + GPT-5.1 评估器，评估准确率 >90%，不同评估器一致性高
  • 丰富的分析维度：推理影响、上下文长度、错误分类、群聊特有模式、定性案例等
  • 揭示了关键洞察：性能差不是长上下文问题而是深度推理问题；Context-Misused 远多于 Context-Ignored
  • 仅覆盖文本上下文：现实生活中的 context learning 本质上是多模态的（图片、视频等）
  • 评估成本高：依赖 GPT-5.1 作为评估器，成本较高；较小的开源评估器存在明显偏差
  • 未提供构建流程细节：因政策限制未公开详细的数据构建过程
  • 群聊场景是特别重要但挑战巨大的方向：模型在多人交互中的身份追踪、角色识别方面表现很差，需要更多针对性研究...

方法核心

尽管 OpenClaw 等系统能力令人印象深刻，自主智能体在日常数字任务中仍表现不佳，对较小 LLM 尤为明显。核心瓶颈在于：

  • 个性化需求多样：不同职业、工作流和日常生活对任务分布的定义提出了挑战
  • 长时程可验证性困难：涉及文件操作序列、工具调用、工作区更新和中间验证，自动化评估非平凡
  • 环境接地要求：需要真实模拟具体的文件系统和工作区 artifact，难以大规模仿制

现有工作在训练算法（ClawR1, MetaClaw）和评测基准（PinchBench 等）方面有所进展，但缺乏一个系统性的框架来统一任务合成、轨迹收集、智能体训练和评测。

作者提出 ClawGym，一个数据驱动的框架，系统性地统一了 Claw-style 个人智能体的任务合成、训练和评测。核心创新在于双路径数据合成策略：自上而下的 persona 驱动路径 + 自下而上的 skill 接地路径，配合自动环境构建和混合验证机制。

ClawGym 框架包含三大组件：

  • ClawGym-SynData：13.5K 合成训练任务的数据集
  • ClawGym-Agents：通过黑盒 rollout 收集高质量轨迹并训练的智能体家族
  • ClawGym-Bench：200 个经人工-LLM 协作审核的高质量评测实例

  • 长时程可验证性困难：涉及文件操作序列、工具调用、工作区更新和中间验证，自动化评估非平凡
  • 环境接地要求：需要真实模拟具体的文件系统和工作区 artifact，难以大规模仿制

现有工作在训练算法（ClawR1, MetaClaw）和评测基准（PinchBench 等）方面有所进展，但缺乏一个系统性的框架来统一任务合成、轨迹收集、智能体训练和评测。

  • 端到端系统性框架：首次将任务合成、轨迹收集、智能体训练和评测统一在一个框架中
  • 双路径互补合成：persona-driven 保证场景多样性，skill-grounded 保证操作接地性，实验验证了混合策略的协同效果
  • 可扩展性强：自动化合成管线使得大规模数据生成成为可能（30K skill → 16K → 13.5K 任务）
  • 混合验证机制：代码+Rubric 的验证方式兼顾了确定性和定性需求
  • 泛化能力好：在内部 ClawGym-Bench 和外部 PinchBench 上均展示显著提升
  • 开源精神：承诺开源代码、数据和基准
  • 与闭源前沿模型仍有差距：ClawGym-30A3B 平均分 56.82 vs Claude-4.7-Opus 77.81
  • 最佳 reward 阈值是经验选择：0.5 的阈值通过实验确定，缺乏理论依据
  • RL 探索有限：RL 管线仅做了初步实验，效果提升相对有限
  • 执行可行性评分相对较低：人工评估中 Execution Feasibility 得分 3.50（满分 5），反映某些任务的环境假设较复杂

问题与动机

长文档、多文档问答在金融、法律、科研分析等场景非常常见，但即便前沿模型已经支持百万 token 上下文，真实文档集合依然会很快超出上下文窗口。常见做法是：

  • 把文档切成 chunk。
  • 在 chunk 上分别抽取或回答。
  • 再把 chunk 级结果聚合成最终答案。

作者认为这里有一个根本性问题，称为 aggregation bottleneck：

  • chunking 虽然缓解了“放不进上下文”的问题；
  • 但随着 chunk 数量增多，系统仍然需要对越来越多的 chunk 级中间结果做二次聚合与推理；
  • 这其实又把问题重新变回了“长上下文整合问题”。

也就是说，很多 long-context 方法并没有真正摆脱长度瓶颈，只是把瓶颈从“原始文档”转移到了“chunk 输出的聚合层”。

这张图对应论文最重要的动机：

  • 传统 chunk-based pipeline 把原文切碎后，虽然局部处理更容易；
  • 但下游还是要把大量局部结果重新拼起来；
  • 随着文档数和 chunk 数上涨，聚合层的负担会迅速膨胀；
  • SLIDERS 的做法是把这些局部信息沉淀到结构化表中，让后续推理在数据库上进行，而不是继续在文本上“拼接后再读”。

“aggregation bottleneck” 这个概念很强，因为它解释了为什么很多方法在工程上看似做了分治，实质上仍然没有解决可扩展推理。

当问题需要强主观判断、模糊语义解释、开放式写作时，数据库表示未必能完整承载所有信息。

方法核心

作者的核心判断是：

  • 真正需要扩展的不是一次性喂给模型的文本长度；
  • 而是系统持久化、组织、查询和整合证据的能力。

所以他们把任务从：

  • “让 LLM 在超长文本里直接找答案”

改写成：

  • “让 LLM 先把文本转换成结构化数据库，再在数据库上做程序化推理”。

这意味着：

  • 文本负责提供原始证据；
  • 关系数据库负责保存显式状态；
  • SQL 负责执行聚合、过滤、比较、算术与跨文档整合；
  • LLM 更像一个 agent，负责 schema 设计、抽取、纠错、查询生成与多轮工具调用。

核心思想：Terminal-World 的核心贡献，是把 agent skill 从“人给 agent 的执行说明”提升为 terminal-agent 数据合成的中心原语，并围绕它联合构建任务、环境与轨迹，从而以很低的数据量和成本，训练出比现有 terminal-agent 合成数据方法更强、更高效的模型。

问题与动机

这篇论文关注的是 terminal agent 的训练数据瓶颈。

和 API agent 不同，terminal agent 不是在固定工具列表里选一个 API 调一下，而是真正在命令行环境中执行 shell 命令、读写文件、安装依赖、跑测试、启动服务、调试环境。作者认为，这类 agent 的训练难点不只是“缺任务”，而是同时缺三样彼此强耦合的东西：

  • 任务指令：到底要 agent 完成什么；
  • 可执行环境：文件、依赖、初始状态、服务配置是否真实可运行；
  • 高质量轨迹：teacher 是否给出了有效、简洁、少走弯路的交互过程。

已有自动化数据构建方法，大多从某种 partial source 出发，比如：

  • 人工种子关键词或短描述；
  • GitHub 仓库；
  • 单一环境组件。

然后再让 LLM 去“把剩下的补完”。作者认为这种思路有三个根本问题：

  • 任务分布受限：因为起点本身很窄，最后合成出的任务也集中在少数种子分布里；
  • 环境和任务不对齐：任务语义和环境不是从一开始共同定义出来的，而是后补的，所以常常 fragile；
  • teacher 轨迹低效：teacher 在没有明确 procedural guidance 的情况下，只能自己探索，容易产生冗余命令和低质量路径。

论文的核心主张是：终端任务的数据构造，不应该从“半成品种子”出发，而应该从 agent skill 出发。

方法核心

作者把 agent skill 当作 terminal-agent 数据合成的中心原语。原因是 skill 天然同时编码了三件事：

  • what：要完成什么能力；
  • when：什么前提条件、环境状态下适用；
  • how：应该怎样执行。

这恰好对应 terminal-agent 训练样本最需要的三部分：

  • 任务指令；
  • 环境构造；
  • 教师轨迹。

所以 Terminal-World 的想法不是“先有任务，再补环境，再让 teacher 去试”；而是：

从 skill 出发，自顶向下联合生成 task instruction、environment blueprint 和 execution guideline，再把它们实例化成可执行 sandbox，并收集 teacher trajectory。

  • Trajectory Collection

  • single skills：单技能；
  • skill teams：同一子类中的多技能、多角色协作；
  • skill graphs：跨子类技能组合成更长的工作流。

论文将现有 Agent Benchmark 分为四类，逐一分析其局限：

Prompt-Driven（如 OneMillion-Bench、CL-Bench）：所有信息嵌入自然语言指令中，零外部文件交互，完全跳过办公工作流的核心媒介。

Open-Source/Environment-Driven（如 OSWorld、GAIA、WebArena）：需通过工具与动态环境交互，但主要聚焦 Action Grounding 或 API 编排，忽略本地文件生态系统中的导航与推理。

Task-File-Driven（如 OfficeQA-Pro、GDPVal）：引入真实文件处理，但直接将任务相关文件打包提供给 Agent，跳过了从复杂文件系统中独立搜索和筛选信息的挑战。

Workspace-Relevant（如 OfficeBench、TheAgentCompany、SWE-bench）：最接近现实，构建了文件系统环境，但存在三大瓶颈：

  • 单一风格文件系统，缺少角色多样性
  • 文件格式覆盖 <10 种，缺少 50+ 种真实办公格式
  • 任务设计缺乏对文件间协同关系的显式评测（聚合、语义关联、版本溯源）

测试 Agent Harness（4 个）：

  • OpenClaw：解耦双环执行架构，高层认知规划与底层工具调用分离，结构化知识存储 + 语义路由层实现跨会话共享记忆
  • Claude Code：高密度推理与深度工作空间集成，原生使用 MCP 和 SKILLs，混合状态控制策略（CLAUDE.md + 动态压缩算法）
  • LangChain DeepAgent：基于 LangGraph 持久 DAG 架构的白盒 Harness，解耦控制流与 LLM，内置规划工具（write_todos）确保执行路径透明可追踪
  • Hermes：内置学习循环的开源 Agent，四层解耦记忆引擎（静态身份指令 + 动态状态文件 + SQLite FTS5 档案），自学习机制将试错经验持久化为本地技能库

测试基础模型（7 个）：Opus-4.7、GLM-5.1、GPT-5.4、Gemini-3.1-Pro、Kimi-2.5、MiniMax-M2.7、Seed-2.0-Code

评估设置：Workspace-Bench-Lite（100 任务），Seed-2.0-Lite 作为 Judge LLM，标准化执行和评估 Prompt。
