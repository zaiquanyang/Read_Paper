方法与框架

现有工作（dLLM-Cache、dKV-Cache、FreeCache、Fast-dLLM）利用相邻解码步 KV 状态几乎相同的观察，将 ARM 的 KV cache 机制适配到 dLLMs：

  • dLLM-Cache：为 prompt cache 和 response cache 设置不同刷新间隔，用特征相似度部分更新 response
  • dKV-Cache：实现一步延迟缓存（decoded tokens 在下一步才被缓存）+ 刷新机制
  • FreeCache：仅缓存 prompt tokens 的 KV 状态（基于 mask tokens 对早期 unmasked tokens 贡献迅速衰减的观察）
  • Fast-dLLM：缓存当前解码 block 之外的所有 KV 状态

核心不足：这些方法仅仅引入了 KV cache，但没有进一步分析 cache 内部特性或对其进行稀疏化。它们存储完整的 KV 表示，导致巨大的内存开销，限制了长上下文场景的实际部署。

Sparse-dLLM 是第一个训练无关 (training-free) 的框架，将动态 cache 驱逐与稀疏注意力集成到 dLLMs 中。核心包含两个策略：

  • 动态双向 cache 驱逐：利用 token 显著性的时间一致性，用注意力感知的稀疏模式动态驱逐前缀和后缀 token 的低重要性 KV 条目
  • 延迟 cache 更新：cache 更新故意延迟一步以提高稳定性；切换到新的解码 block 时完全刷新 cache

与 ARM 只能稀疏化前缀 token 不同，Sparse-dLLM 同时针对前缀（当前 block 之前的 token）和后缀（当前 block 之后的 token）进行驱逐。

设 $b$ 为 block 长度，$p$ 为 prompt 长度，$o \in [p, L)$ 为当前 block 首 token 的位置偏移。当前 block 之外的候选 KV 状态：

$$\mathbf{K}_f = \text{Concat}[\mathbf{K}_{:o}, \mathbf{K}_{o+b:}], \quad \mathbf{V}_f = \text{Concat}[\mathbf{V}_{:o}, \mathbf{V}_{o+b:}]$$

通过当前 block 的 query 状态 $\mathbf{Q}_b$ 计算注意力分数：

$$\mathbf{A} = \frac{\mathbf{Q}_b \mathbf{K}_f^T}{\sqrt{d_k}}$$

借鉴 SnapKV，引入 max pooling 聚合局部信息（防止驱逐后数据不完整导致性能退化）。设 $r$ 为保留比，$s$ 为 max pooling 核大小，通过 top-$k$ 选择 pivotal token 索引（$k = (L-b) \times r$）：

$$\text{Indices} = \text{top-}k(\text{MaxPool}(\mathbf{A}))$$

最终 cache 只保留选中的 KV：

$$\mathbf{K}_c = \mathbf{K}_f[\text{Indices}], \quad \mathbf{V}_c = \mathbf{V}_f[\text{Indices}]$$

算法伪代码（Algorithm 1）：

  • 提取当前 block 之外的 KV 状态（前缀+后缀拼接）
  • 计算 block query 的平均值 $\bar{q} = \text{Mean}(\mathbf{Q}_b)$
  • 计算注意力分数 $\mathbf{A} = \text{MatMul}(\bar{q}, \mathbf{K}_f^T)$
  • MaxPool1D 聚合 → TopKIndices → 选出 pivotal token 的 KV
  • 更新 cache

实验与结论

  • 模型：LLaDA-8B-Instruct、LLaDA-1.5、Dream-v0-7B-Base、Dream-v0-7B-Instruct
  • 默认超参：block length=32，保留比 $r=0.5$，max pooling 核大小 $s=3$，随机种子 2025
  • 基线：vanilla dLLM、dLLM-Cache、dKV-Cache、Fast-dLLM
  • 评估指标：Accuracy（3 次独立实验均值）、Throughput (TPS)、Peak Memory (GB)
  • 基准测试：MMLU (5-shot)、ARC-C (0-shot)、PIQA (0-shot)、GPQA (5-shot)、GSM8K (4-shot)、Math (4-shot)、HumanEval (0-shot)
  • 硬件：NVIDIA 4090 (48GB)
  • 评估工具：OpenCompass

关键结论：

  • Sparse-dLLM 吞吐量提升 3.4×（平均），远超所有基线（Fast-dLLM 2.2×、dLLM-Cache 2.3×）
  • 内存与 vanilla dLLM 几乎相同（1.0×），而其他 cache 方法增加 10-20% 内存
  • 性能保持可比，在 ARC-C、PIQA 等任务上达到最优

价值、局限与启发

现有工作（dLLM-Cache、dKV-Cache、FreeCache、Fast-dLLM）利用相邻解码步 KV 状态几乎相同的观察，将 ARM 的 KV cache 机制适配到 dLLMs：

  • dLLM-Cache：为 prompt cache 和 response cache 设置不同刷新间隔，用特征相似度部分更新 response
  • dKV-Cache：实现一步延迟缓存（decoded tokens 在下一步才被缓存）+ 刷新机制
  • FreeCache：仅缓存 prompt tokens 的 KV 状态（基于 mask tokens 对早期 unmasked tokens 贡献迅速衰减的观察）
  • Fast-dLLM：缓存当前解码 block 之外的所有 KV 状态

核心不足：这些方法仅仅引入了 KV cache，但没有进一步分析 cache 内部特性或对其进行稀疏化。它们存储完整的 KV 表示，导致巨大的内存开销，限制了长上下文场景的实际部署。

  • 训练无关、即插即用：不需修改模型或重新训练，直接加速任何预训练 dLLM
  • 吞吐量大幅提升：平均 3.4-3.6× 加速，长上下文最高 10×，远超所有现有 cache 方法
  • 内存效率最优：与 vanilla dLLM 几乎相同（甚至更低），而其他 cache 方法增加 10-30% 内存
  • 长上下文可扩展：内存增长曲线几乎平坦，其他方法会 OOM
  • 性能保持甚至提升：在某些任务（如 Dream 上）平均精度超越基线
  • 双向稀疏化：同时驱逐前缀和后缀的低重要性 KV，充分利用 dLLM 双向注意力的特性
  • 代码任务表现下降：HumanEval 上 Sparse-dLLM 弱于基线和完整 cache 方法——代码任务可能需要完整上下文
  • Pivotal tokens 多为无语义 token：当前策略保留的 pivotal tokens 主要是换行符和空格，未来可探索更细粒度的语义感知驱逐
  • 超参数需设置：$r=0.5$、$s=3$ 是经验最优，可能在不同模型/任务上有差异
  • 延迟策略固定：当前固定延迟 1 步，N-step 延迟消融显示 3 步延迟准确率更高但吞吐量下降，自适应延迟值得探索
  • 未与训练阶段结合：如果训练时就考虑稀疏注意力模式，可能进一步提升性能
