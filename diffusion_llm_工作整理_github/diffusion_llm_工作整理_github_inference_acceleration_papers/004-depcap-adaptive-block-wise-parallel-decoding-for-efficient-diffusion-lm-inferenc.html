DepCap: Adaptive Block-Wise Parallel Decoding for Efficient Diffusion LM Inference

abs | pdf | https://github.com/X-Xia0828/DepCap | summary md

作者：Xiang Xia, Wuyang Zhang, Jiazheng Liu, Cheng Yan, Yanyong Zhang

机构：University of Science and Technology of China; Institute of Artificial Intelligence, Hefei Comprehensive National Science Center

一句话总结

DepCap 是一个 training-free 的 block-wise DLM 推理加速框架：它用上一个 decoded block 对未来位置预测分布的 KL 变化来动态决定下一个 block 的边界，并用 conflict score 过滤当前 block 内可安全并行提交的 token，从而在 LLaDA/Dream 等 DLM 和 GSM8K、Math-500、MBPP、HumanEval 等任务上获得更好的 speed-quality trade-off，最高报告 5.63x speedup，且可与现有 KV-cache 技术叠加。

背景与动机

Diffusion Language Models (DLMs) 的潜力在于可以并行更新多个 token，并对整段序列进行 global refinement。为了把这种并行潜力转化为实际推理速度，近年的 DLM inference 通常采用 block-wise decoding：把待生成序列切成若干 block，按 block 顺序解码，每个 block 内再做扩散式并行更新。

但 block-wise DLM inference 有两个关键决策：

  • 下一个 block 应该扩多长，也就是 block boundary 如何决定。
  • 当前 block 内哪些 masked positions 可以安全地并行解码。

已有方法在这两点上都偏保守或不够匹配 DLM 的动态特征：

  • Fast-dLLM 等方法多用固定 block size，忽略不同样本、不同生成阶段的依赖范围变化。
  • AdaBlock、Swordsman、GeoBlock 等动态 block 方法主要依赖当前 step 的语义符号、entropy 或 attention 几何信号，没有充分利用多步 denoising 中“上一个 decoded block 对未来位置的影响”。
  • confidence-based parallel decoding 只看单点 confidence，高 confidence 并不保证多个 token 可以同时提交，因为它们之间可能存在相互依赖或冲突。

DepCap 的核心观点是：block-wise DLM 的两个决策需要不同、更合适的信号。block boundary 应该用跨 step 的 last-block influence；block 内并行提交应该用 token-level conflict signal。

方法与框架

DepCap 是一个 training-free、plug-and-play 的 DLM 推理框架，由两个模块组成：

  • DepGA-Block: Dependency-Guided Adaptive Block Partitioning，用上一个 decoded block 对未来位置预测分布的影响，动态决定下一个 block 的边界。
  • CAP-Decoding: Conflict-Aware Parallel Decoding，在当前 block 内筛选 conflict-free token subset，避免把互相依赖或冲突的 token 同时解码。

图中左侧是传统 block-wise DLM：固定 block size，并用 confidence-only parallel decoding。右侧是 DepCap：先用 last-block influence 和 predictive uncertainty 决定 block boundary，再用 conflict-aware 策略过滤当前 block 内可并行提交的 token。

实验与结论

评测模型：

  • LLaDA-8B-Instruct
  • Dream-v0-base-7B
  • LLaDA-1.5

评测任务：

  • GSM8K，5-shot
  • Math-500，4-shot
  • MBPP，3-shot
  • HumanEval，0-shot

指标：

  • Acc: 任务准确率
  • TPS: tokens per second，越高越快
  • NFE: number of function evaluations，越低表示 denoising 调用越少

默认超参：

  • generation length L_gen = 256
  • DepGA-Block: lambda=1.2, L_min=8, L_max=128
  • CAP-Decoding: tau_low=0.8, tau_high=0.95, gamma=-16.0
  • confidence baseline threshold: 0.9
  • fixed block sizes: {16, 32, 64}
  • 硬件: single NVIDIA A100 40GB
  • benchmark framework: lm-eval

论文的主结果表很大，覆盖三类 backbone 和四个任务。关键结论如下。

论文把 DepCap 拆成两个模块来分析：

  • Confidence + DepGA-Block: 只替换 block partitioning，不用 CAP-Decoding。
  • CAP-Decoding + fixed block: 只替换 block 内 parallel decoding，不用 adaptive block。
  • DepGA-Block + CAP-Decoding: full DepCap。

结论：

  • DepGA-Block 更偏向提升 accuracy/稳定性，因为它用 last-block influence 控制 block 边界，避免过早扩到高不确定区域。
  • CAP-Decoding 更偏向提升 speed，因为它比 confidence-only 更敢于并行提交 token，但通过 conflict filtering 控制风险。
  • 两者结合时，通常得到最佳 overall speed-quality trade-off。

也就是说，DepCap 的两个模块不是重复贡献，而是分别解决外层 block boundary 和内层 token subset selection。

价值、局限与启发

  • 问题拆解准确：block-wise DLM inference 的瓶颈被拆成 block boundary 和 within-block parallel subset 两个决策。
  • DepGA-Block 使用 cross-step signal，比只看当前 step 的 entropy/confidence 更贴合 diffusion iterative denoising 的动态。
  • CAP-Decoding 明确处理 token conflict，弥补 confidence-only 的不足。
  • Training-free，可插到多个 DLM backbone 上，也能与 prefix/dual cache 结合。
  • 实验覆盖 reasoning 和 coding tasks，且包括 LLaDA、Dream、LLaDA-1.5 多个模型。
  • 附录给出了信息论解释和较完整的超参数敏感性分析。
  • 理论部分只是信息论解释和近似，没有严格 bound。作者也在 discussion 中承认需要更强形式化保证。
  • DepGA-Block 的 implemented score 是理论 expected influence 的 sample/approximation，依赖 logits 前后变化是否能稳定反映真实 dependency。
  • 在 Dream 系列上，full DepCap 不总是 accuracy 最优，部分任务存在 accuracy drop。
  • 主表很大但缺少显著性分析、多 seed 方差和更细的失败案例。
  • 方法主要针对 block-wise decoding；作者提到 sliding-window diffusion decoding 是未来方向，当前还没有覆盖。
  • CAP-Decoding 的 conflict score 是轻量 heuristic，是否能泛化到更长上下文、更复杂语义依赖仍需验证。

DepCap 和前面读过的 DIP 有很强的互补性：

  • DIP 关注动态 context/examples 什么时候插入；
  • DepCap 关注生成区域如何自适应分块，以及 block 内哪些 token 可以并行提交。

两者都在利用 DLM 不是严格 left-to-right 的特点，把“固定推理计划”改成“基于中间状态的动态调度”。后续可以考虑：

  • 把 last-block influence 扩展到 dynamic context scheduling：判断新插入 example 是否真的改变未来 token distribution。...
